## Sessions Mabari runs

Mabari runs a Claude Code session as a child process, in `internal/connectors/claudecode/run.go`:

```
claude -p --input-format stream-json --output-format stream-json --verbose
  --include-partial-messages --permission-mode default --permission-prompts none
  --settings <hooks as JSON> (--session-id <uuid> | --resume <uuid>)
  [--name] [--model] [--agent] [--disallowedTools] [--max-budget-usd]
```

**Not verified against the real program.** Nobody has run `claude` for this, by rule, because it spends the account. These are the docs' words, tested against `internal/connectors/claudecode/fakeclaude`, which follows them. Before relying on this, try it once by hand with a throwaway session, and check first that a risky command stops for a click and that no answer denies it. Three things the docs leave open are written to work either way: whether SIGINT leaves the process running, whether `--resume` keeps the session id (the docs imply it does), and in which order a denial's `permission_denied` message and its `tool_result` arrive.

### Why a risky action stops for a click

What Mabari relies on, each from the docs:

- `claude -p` runs in Manual mode when nothing sets a mode (v2.1.302 or later), and `--permission-mode` outranks every settings file, so Mabari always passes it. `manual` is an alias for `default` from v2.1.200.
- "In sessions that can't show a prompt [...] Claude Code still runs these hooks, and if no hook returns a decision, it denies the tool call." `PermissionRequest` also fires "when it would otherwise auto-deny a call that can't prompt". `--permission-prompts none` (v2.1.259 or later) says the same outright: anything that would prompt "is denied unless a `PermissionRequest` hook allows it".
- So every failure denies: a hook that fails, times out, or can't reach Mabari, or Mabari not answering. Mabari's hook allows only on a person's click or auto approve. With no click in `SessionPermissionWait` (30 minutes) it answers deny.
- `permissions.allow` rules skip the prompt, so `PermissionRequest` never fires for them. Mabari's `PreToolUse` hook therefore answers `ask` for what `internal/risk` calls risky, for `Bash`, `PowerShell`, the edit tools, `Read`, `WebFetch` and `mcp__*`. "When multiple PreToolUse hooks return different decisions, precedence is `deny` > `defer` > `ask` > `allow`", so this outranks any other hook's allow. In a Mabari session, a command with an allow rule still needs a click if Mabari's rules call it risky, which is stricter than a terminal.
- Gating hooks pass `--run`, which exits 2 when Mabari can't be reached, and set `onFailure: "block"`, which on `PermissionRequest` "denies the request".
- `system/init` reports `permissionMode`. A session reporting anything but `default` or `plan` is ended at once. This should only happen under managed settings.
- No flag grants anything. `--dangerously-skip-permissions`, `--allow-dangerously-skip-permissions`, `--allowedTools` and `--permission-prompt-tool` are never passed, and the fake refuses them.
- **`--bare` must never be passed.** "Hooks still don't run in bare mode when you pass them with `--settings`." The docs say bare "will become the default for `-p` in a future release". If that happens, every approval is denied, which is safe but makes sessions useless. Re-check this on each upgrade.

### What can still get past a click

- **A folder's own code.** "A `-p` session shows no workspace trust dialog", and a repository's hooks, `env` block, helper commands, a project skill's hooks and `allowed-tools`, and `.mcp.json` servers all run in a folder never trusted. A repository's `PermissionRequest` hook could answer allow by itself. Its `permissions.allow` rules are not used under `-p`, and `bypassPermissions` from project settings doesn't take effect. So `FolderConfig` looks for these, up to the repository's root, and Mabari asks for a click before starting there, once per folder (`POST /api/folders/trust`). Mabari's own replies can't give that click.
- **What the person installed themselves.** Hooks in their own `~/.claude/settings.json` run as they always do. A mod handling `tool.check` can approve what a `PreToolUse` hook would prompt for, unless managed settings or a Team or Enterprise login are in place. `--safe-mode` would stop that but also turns off CLAUDE.md, skills and more, so Mabari doesn't pass it.

### Hooks per process

Hooks go in `--settings`, so a session runs with nothing written to `settings.json` and nobody attached. Hooks from `--settings` merge with those in settings files, so with Claude Code attached both sets fire. Mabari's own carry `--run`, sent as the `X-Mabari-Run` header, and the settings-file copy is ignored for a session with a live process. `MessageDisplay` is left out because the stream carries every message.

### Limits

- `AskUserQuestion` and `ExitPlanMode` are offered in `-p` "only when the run has a permission host", and Mabari has none, because an MCP `--permission-prompt-tool` couldn't be tested here. So Claude asks questions as plain text, and the person answers with a message. A plan session stops at its plan, Mabari asks with an approval, and approving starts the process again with `--resume --permission-mode default`. `-p --resume` doesn't restore a stored permission mode.
- The session's first message goes on stdin, so a slash command in it runs as typed ("user-invoked skills and custom commands work").
- `--max-budget-usd` stands in for the daily cost cap. It is per process, not per day, and totals restored on resume don't count towards it.
- `total_cost_usd` is a running total, resumed sessions included, and a client-side estimate. `usage` covers one turn.
- Windows has no signals, so Interrupt and Stop are a kill, and the session resumes. Compiled there, not run.
- After a crash, children end when stdin closes at the end of their turn. On the next start, a leftover process is ended if its command line holds its session id.
- `MABARI_NO_SESSIONS=1` means the server can't start sessions. The end-to-end tests' shared server sets it. Only `findClaude` in `cmd/mabari` looks `claude` up on PATH, so Go tests can't reach the real program.

### Sessions started elsewhere

- Read from `transcript_path`, only read, and only a `.jsonl` file inside Claude Code's `projects` folder. The docs say the format "is internal to Claude Code and changes between versions", so unknown lines are skipped and a broken format costs the conversation, never the session. The file "may lag", so what shows follows a little behind.
- "If you resume the same session in two terminals without forking, messages from both interleave into one transcript." Hook input doesn't say whether a session is still open, so taking one over needs `confirm: true`, after the person is told.
- A session Mabari ran that reports through settings hooks with no process behind it has been continued in a terminal, so it goes back to being followed.

## The conversation API

Package 5 draws this and package 6 sends to it. Types are in `internal/models/conversation.go`, generated into `web/src/gen/models.ts`.

`GET /api/agents/{id}/conversation?before=<seq>&limit=<n>` returns `Conversation`: `{agentId, items, hasMore}`, oldest first. The default limit is 200 and the most is 500. For older history, pass the first item's `seq` as `before`. An agent that has left keeps its conversation until retention removes it. Only an id nothing was ever said to gives 404.

`ConversationItem`:

| Field | Meaning |
|---|---|
| `id` | Stable across updates. Replace what you hold. |
| `seq` | Order within the agent. Only ever goes up. Order by this, not `time`. |
| `kind` | `user`, `assistant`, `tool` or `notice`. |
| `text` | Secrets masked. Empty for a tool call. |
| `streaming` | True while text is arriving through deltas. |
| `tool` | For a tool call: `name`, `summary` (one line), `input` (JSON text), `output`, `state` (`running`, `done`, `failed`, `denied`). |
| `from` | For `user`: `mabari`, or `session` if typed in the session's own window. |
| `parent` | The tool call of the subagent this came from, or empty. |
| `clipped` | Something was cut. Text is cut at 100,000 characters, and tool input and output at 16,000. JSON over 256 KiB can't be masked in part, so it isn't kept. |

Live changes come over the WebSocket:

- `{type: "conversation", item}` adds an item, or replaces the one with its `seq`.
- `{type: "conversation.delta", id, agentId, text}` appends to a streaming item. Deltas are not stored: the finished item replaces them, and a page that missed some gets the whole text then.

On `resync` or `reset`, reload what is open: conversations aren't in the snapshot. `web/src/data/conversation.ts` does all of this.

`LiveAgent.session` is the session behind an agent: `{id, status, mode, agentFile, started, resume, pid}`, or null. `status` is `running`, `resumable` or `elsewhere`, and `resume` is the exact command for a terminal.

- `POST /api/agents/{id}/session/resume {confirm}` lets Mabari run a session and sends what is waiting. For a session started elsewhere it answers 409 without `confirm: true`.
- `POST /api/agents/{id}/session/release` ends the process and keeps the session resumable.
- `POST /api/folders/trust {path, confirm}` is the person's click. Anything that starts a session can answer 409 with `{error, trust: {folder, found}}`, and `request()` in `web/src/data/api.ts` asks and retries by itself.

Everything goes through `Engine.Converse`, which masks and cuts inside the office lock, so the cost is bounded before masking starts. JSON tool data is masked by key, and only text that isn't JSON falls back to text patterns. A wipe or `ClearOffice` drops the replay history and changes the boot id, so a page resuming from before it reloads rather than being sent deleted text.

## The message box API

The Chats screen (`web/src/chat/`) sends and completes through these. Everything is local, nothing calls a model, and no message can approve anything: it is text, and it goes the way every instruction goes.

- `POST /api/chat/send {agentId | projectId, text, plan, model, now, everyone, attachments, mentions}` is the one send. It adds what the box added: each attachment's stored path (only ids Mabari handed out count), and the latest reply of each mentioned agent, quoted. `plan` runs the next turn of a session Mabari runs in plan mode when it is between turns, so Claude Code holds it to a plan and Mabari asks with an approval; for anything else, and mid turn, it puts a request to plan first in the words. `model` switches a session Mabari runs between turns (the process starts again with `--resume --model`, after the old one has let go of the session), and a demo agent; any other agent answers 409 with why. `now` interrupts a working session Mabari runs and sends straight after, and never when an approval or question is waiting. `everyone` sends a project's message to each lead there that isn't in an error, and records it. Answers `{notice, agentId, instructionId, queued, opened, ask}`.
- `GET /api/chat/files?agent=|project=&q=` lists files and folders in the folder Mabari already knows for that agent or project, never from a path the page sends: no links, no `.git`, `node_modules` or dot files unless asked for, at most 12, within 400 ms and 20,000 entries.
- `GET /api/chat/commands?agent=|project=` lists `commands/*.md` and `skills/*/SKILL.md` under the folder's `.claude` and the account's config folder (`CLAUDE_CONFIG_DIR`, or `~/.claude`), with the first line of each description, and the saved instructions. A name nothing here knows is sent unchanged: Claude Code decides what it means.
- `POST /api/attachments?name=` keeps one file (at most 25 MB) under the data folder in `attachments/<id>/<name>`, with the name cut to one safe part. They are never served back, go with a wipe, and go after the retention setting.
- A file attached for a session Mabari runs is read with no click, for that agent's session only. Attachments sit outside the session's folder, so Claude Code would ask, and Mabari's risk rules would too. Mabari's `PreToolUse` hook answers `allow` for the `Read` tool on that exact path, which Claude Code 2.1.318's hooks reference documents as skipping the permission prompt (except for network paths). `--add-dir` isn't used: it only applies when a process starts, and it opens a working directory, editing included. Nothing is granted after a restart of Mabari, where a read asks again, and any other tool or path takes the usual route. Checked against the docs and `claude --help` of 2.1.318 and the fake, not a real session.
- `GET|POST /api/saved-instructions`, `DELETE /api/saved-instructions/{id}` keep instructions in `saved-instructions.json` in the data folder. They stay through a wipe, like agent files.
- `POST /api/agents/{id}/hand {itemId, to, note}` hands one of the agent's replies to another agent, with where it came from and what it answered. The text is read from the stored conversation, so a page can only hand over what was really said. The sender's thread gets a notice.
- `GET /api/projects/{id}/asks` lists the messages sent to everyone on a project, so their replies, which are each agent's next messages, can be shown side by side after a reload.

Claude Code facts this relies on, all from the docs read for the session work and not tried against the real program: `--permission-mode plan` starts a process in plan mode, `--model` takes a model name, `--resume` keeps the session. `@file` is left in the text as typed, which Claude Code reads as a mention.
